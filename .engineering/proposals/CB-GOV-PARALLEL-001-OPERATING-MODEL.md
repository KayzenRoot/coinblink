## Admission and execution sequence

1. Finish M00 under its admitted Work Order, including the protected corrected-main Preview, exact-SHA route/header/isolation evidence, Owner review, and full M00 DoD/checkpoint closeout. This proposal does not satisfy any of those gates.
2. Obtain the Owner's global product Scope/Architecture/DoD decisions for Issue #6, resolve the roadmap's single-critical-path policy against this proposal, and promote an explicit ADR/source-pack decision through normal GEF review and merge. This proposal alone cannot do that.
3. For each module, freeze its domain contract, dependency SHAs, external authorization gates, tests, exclusive file allowlist, Work Order, and Context Lock. Admit that one Work Order canonically before its agent writes application code.
4. Contract/mock preparation may run independently before code admission only as clearly labelled `PROPOSED` documents and deterministic local fixture specifications in module-owned proposal paths. It may not implement runtime source, migrations, live providers, credentials, billing, deployment, or publication behavior.
5. Start one local Codex Desktop agent in one fresh managed worktree and branch per admitted module Work Order. Record both the immutable admitted/source `baseMainSha` and the current `integrationBaseSha`. Each PR's changed-path/fingerprint set is calculated against its integration base; after incorporating newer main, refresh that value and its evidence while preserving the original source provenance. No agent shares a mutable checkout or branch.
6. Parallel authoring is allowed only if exclusive path manifests are disjoint and dependencies/interfaces are already frozen. One module, one Work Order, one evidence bundle, one PR. Cross-module refactors are separate steward-owned work with an ADR and affected-owner review.
7. Merge PRs to `main` serially until a merge queue is configured and verified to run `merge_group` checks on the exact queued tree. After every merge, update remaining same-wave branches by a normal merge from current main (never rebase/force-push), then rerun exact-head tests/reviews against the resulting candidate. If the update creates a conflict or expands the allowlist, stop for steward arbitration.
8. Only an Owner-authorized merge promotes a module. Read back the resulting main checkpoint and keep progress at its measured value; a PR, mock, draft contract, green CI, or preview does not mark a module complete.

## Agent, branch, Work Order, and PR isolation

For each admitted module, the scheduler assigns exactly one dedicated local Codex agent to a new managed worktree named `cb-m{nn}-wo-{sequence}` and branch `codex/cb-m{nn}-wo-{sequence}`, derived from the active execution Work Order ID. Before creating or resuming, inspect local refs, remote refs, `git worktree list --porcelain`, and the active Work Order registry; if any name or path exists, stop and allocate a new authorized Work Order ID. Never reset, delete, or reuse an existing checkout. Record the Codex task ID, agent identity, initial/final HEAD, integration base, branch/worktree, and clean/dirty state in the Evidence Bundle. Host slot limits are a concurrency ceiling: queue eligible work and assign the next isolated agent when a slot is free. No task is started for an unadmitted module. The Work Order pins base SHA, source fingerprints, exclusive/shared paths, contract versions, prerequisites, tests and stop conditions. Its Context Lock and Evidence Bundle are unique to that ID. The PR title begins `[{workOrderId}]`; corrections stay on the same PR. The mapping in the matrix is a plan only; no future agents, worktrees, branches, Work Orders, or PRs are created by this governance proposal.

One Integration Steward owns the reserved shared paths, prepares route/composition/registry/schema/build/CI wiring after module contracts are reviewed, and handles conflict arbitration. Steward authority is limited to composing already admitted module exports: it cannot admit a module, change accepted scope/security/architecture/DoD, approve or merge a PR, or weaken a check. Where a change cannot be isolated without an unapproved shared-path edit, serialize it or stop for a separate Owner decision.

## File ownership and conflict rules

For future per-module Work Orders after this proposal is adopted, exclusive roots are generated from module ID and Work Order ID in the matrix: `src/modules/CB-Mxx/**`, `test/modules/CB-Mxx/**`, `test/fixtures/modules/CB-Mxx/**`, `e2e/modules/CB-Mxx/**`, its one `docs/architecture/contracts/CB-Mxx.md`, Work Order, Context Lock and evidence files. Comparisons are case-insensitive and slash-normalized for Windows and Linux. No two future module agents may claim overlapping roots. The exact `exclusive_paths` list is frozen per admitted Work Order; these templates do not authorize directories to be created now. M00 is a deliberate transition exception: its already active Work Order/Context Locks remain authoritative until closure; it runs before Wave A and cannot overlap with other module code. M18 remains unscheduled and has no active agent/worktree/branch/Work Order.

The Integration Steward reserves route registration (`src/pages/**`), shared layouts/styles, middleware/env declarations, shared contracts and registries, cross-module schemas/migrations, package manifests/lockfiles, Astro/Wrangler/Docker configuration, CI workflows, and canonical governance/checkpoint files. Module agents do not edit those paths. A module's private schema/migrations, if architecture approval permits them, remain under its own module root. No shared-file edit is accepted without an explicit steward-owned Work Order, ADR where required, and a reviewed change manifest.

Ownership check is fail-closed: compare every added, modified, renamed, and deleted Git path against the frozen Work Order manifest and Work Order allowlist, using the current `integrationBaseSha`, not the original source SHA after a normal main update. Parse NUL-delimited Git output with rename detection disabled so a rename is represented as an old-path deletion and new-path addition. Duplicates, missing paths, unexpected paths, a deletion without an explicit reason, or an exclusive-root collision block the PR. Never use last-writer-wins or resolve a collision by silently broadening another module's allowlist.

## Contract, interface, and mock rules

The reusable contract template is [CB-MODULE-CONTRACT.md](../templates/CB-MODULE-CONTRACT.md). Module-specific interfaces remain unapproved until the relevant module contract is reviewed under its admitted Work Order. Every contract names its producer/consumer, version, canonical DTO/schema, nullability, validation, error semantics, timeout/retry/idempotency rules, auth/privacy boundary, provenance/freshness, resource/cost limit, compatibility policy, and contract tests.

The producer module owns its canonical contract document. Consumers import or test against the reviewed producer contract and may not silently edit it. A breaking contract change requires producer and affected-consumer review, compatibility tests, steward arbitration, and a separate ADR if it changes shared architecture/schema. Fakes are deterministic, local, synthetic, and isolated by module; test jobs have no provider credentials or external network access, expected provider calls are zero, and evidence labels distinguish `MOCK` from `LIVE`. Tests cover expected errors and fallbacks. Live external APIs, credentials, payments, ads, social publication, financial claims, and production bindings remain disabled until their separate Owner/legal/provider gates pass.

The verified base already runs `verify-exact-head`, locked install, `npm audit --audit-level=high`, lint, Astro typecheck, `npm test` (unit/build/Playwright), Linux Docker smoke, and Ubuntu/Windows exact-head GEF jobs. Current GitHub integrations also report CodeRabbit, SonarCloud, and Socket checks on PR #41. This proposal does not change the workflow or claim an unrun gate.

Before adopting parallel code work, CI must additionally prove the Work Order path-manifest set equals the actual Git change set, the dependency DAG is acyclic, module-exclusive roots do not overlap, contract consumers match their frozen versions, and the tested checkout SHA equals the PR head. An integration test must run on each serialized post-merge main. A verified merge queue may replace serialized merge checks only after `merge_group` is covered by the exact-head workflow. Module-specific tests include contract conformance, deterministic mocks, unit/integration/E2E, a11y/security/performance as applicable, build/typecheck/lint, Docker or Preview smoke as authorized, and applicable provider-negative tests.

Each Work Order's Evidence Bundle records the WO/task/agent IDs, immutable base and current integration-base/head/dependency SHAs, branch/worktree and clean/dirty state, changed-path owner/status manifest, Context Lock and source fingerprints, contract versions, exact commands/exit codes, unit/contract/E2E/a11y/security/build/Docker or Preview artifacts, mock-vs-live mode and provider-call count, external approvals/cost gates, live branch-protection and merge-queue state, exact-head CI links, independent reviewer identity/commit, Owner audit, migration state (`none` or approved sequence/apply/rollback evidence), risks, and proposed checkpoint delta. No secret values are recorded. Evidence is factual: candidate/draft status, failed or skipped checks, partial-resource uncertainty, and unresolved provider gates remain explicit.
